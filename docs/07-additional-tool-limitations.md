# PlanReader — Additional Tool Limitations & What They Mean for the Build

Deeper digging into GitHub issues, maintainer blog posts, and real troubleshooting threads surfaced limitations that are more specific and more actionable than what a marketing/pricing-page comparison shows. These are organized by theme, each with the concrete evidence and what it should change in PlanReader's design.

## 1. Malformed input is a first-class problem, not an edge case

- **Postgres itself has generated invalid JSON.** < cite index="104-1">Dalibo found and reported a PostgreSQL bug where JSON plans could contain duplicated keys (e.g. two "Workers" keys in the same object), which is invalid JSON — `JSON.parse()` in JavaScript doesn't error on this, it silently keeps only one of the duplicated keys, so information is quietly lost rather than the parse visibly failing</cite>. < cite index="104-1">PEV2's fix was to stop using the browser's native JSON.parse and instead stream-parse with a dedicated library so duplicate keys can be merged instead of dropped</cite>. Years after the underlying Postgres bug was fixed, < cite index="104-1">plans generated on old, still-buggy Postgres versions are still submitted to explain.dalibo.com, though at a shrinking rate (under 3 per 1000 recently)</cite>.
  - **Implication**: PlanReader's Postgres JSON parser cannot use naive `JSON.parse()`. It needs a duplicate-key-tolerant parser from day one, plus a quiet "this plan looks like it came from an old/buggy Postgres version" note rather than a silent data-loss bug or a hard failure.
- **`auto_explain` has its own history of invalid-JSON output** — a long-running core mailing list thread shows `auto_explain`'s JSON output not matching the structure `EXPLAIN`'s own JSON formatter produces, which broke tools expecting the standard shape. Anything captured from log files (a very common real-world source, since `auto_explain` is how people catch intermittently-slow queries) is a distinct input shape from copy-pasted `psql` output and needs its own tolerant-parsing path, not an assumption that "JSON is JSON."
- **Common copy-paste mangling breaks naive parsers.** < cite index="92-1">Postgres output copied after running `\x on` in `psql` (a very common habit when browsing data) produces plan text wrapped in `[ RECORD ]` markers and a `QUERY_PLAN` header that a plan parser chokes on, even though stripping those lines is straightforward</cite>.
  - **Implication**: build a small pre-processing/cleanup pass that strips known copy-paste artifacts (`\x`-mode record markers, psql headers/footers, leading `LOG:`/timestamp prefixes from log-captured `auto_explain` output) before the real parser ever runs — this is cheap to build and directly prevents the single most common "why won't this just work" first-impression failure.
- **SQL Server XML is frequently not rooted the way people expect.** < cite index="63-1">The `ShowPlanXML` node is often not the root of the XML a person has — Extended Events wraps it in additional information, so a parser that assumes `ShowPlanXML` is the document root will fail on very commonly-captured plan exports</cite>.
  - **Implication**: the SQL Server parser should search the document for a `ShowPlanXML` element rather than assume it's positioned at the root, and should handle at least the Extended-Events-wrapped case explicitly, since it's a common capture method, not a rare one.

## 2. Parallel-query stats are a persistent, unresolved source of confusion

- < cite index="89-1">PEV2 users have reported that cumulated I/O timings across parallel workers make a fast query look absurdly slow — 178MB read in both a serial and parallel run, but the parallel run displayed 5s instead of 500ms, because per-worker timing appears to be summed rather than shown as a per-worker or max-across-workers figure</cite>, and < cite index="89-1">the maintainers acknowledge this may be expected Postgres behavior that the tool should at least label clearly ("cumulated") rather than present as a single misleading duration</cite>.
- < cite index="90-1">A related open issue shows a Seq Scan reporting a "1s 322ms" duration for a node that only touched 9 rows across 3 loops — a case where the naive "actual time × loops" duration math produces a number that looks alarming but is actually a display/interpretation issue, not a real problem</cite>.
  - **Implication**: this is exactly the kind of trap a plain-language rule engine can either walk straight into (amplifying a beginner's confusion by confidently labeling a misleading number as "this is your slowest node!") or actively defuse (detecting parallel/looped nodes and explicitly noting "this time is summed across N workers/loops — the real per-execution time is roughly X"). This should be a named rule in the MVP rule set for all three engines wherever loop/worker counts exist, not an afterthought.

## 3. A single captured plan cannot diagnose parameter-sensitivity problems — and this is a category-level limitation worth being upfront about

- Research into SQL Server's parameter sniffing confirms a structural fact that applies to any plan-explanation tool, including PlanReader: < cite index="121-1">a parameterized query can get a plan compiled for one set of parameter values and then run badly for a different set of values — pasting the exact same query into a tool and re-running it can produce a fast result even though the application is timing out, because the tool sees a fresh compile, not the cached plan that's actually causing pain in production</cite>. Snowflake has a related but distinct issue: < cite index="115-1">a query owner has no direct control over how the query executes once submitted, because Snowflake's cost-based optimizer dynamically determines the plan, so a query that ran fine for a year can suddenly get a different plan and time out with no code change</cite>.
  - **Implication**: this isn't a bug PlanReader can fix by parsing harder — a single pasted plan is, by definition, a single snapshot. The honest and differentiating move is to say so explicitly in the tool's output whenever it detects a parameterized query or a plan whose costs look unusually mismatched from what the shape would suggest: a short, plain-language note like "this plan reflects one specific run — if this query is sometimes fast and sometimes slow, the cause may be a different plan being used for different input values (parameter sniffing / plan sensitivity), which a single pasted plan can't show you." No competitor tool reviewed makes this limitation clear to a beginner user, and stating it costs nothing to build while meaningfully building trust and steering advanced users toward Query Store / plan-history tooling (a natural pgsuite/QueryDoc mention) rather than letting them assume the single plan is the whole story.

## 4. Free-tier and access friction, concretely

- < cite index="17-1">pgMustard's free trial is capped at five of the user's own real query plans, with no time limit but a hard usage ceiling</cite> — so "free" in the existing competitive set almost always means "free for a handful of uses," not genuinely unlimited. PlanReader's zero-cap, zero-signup rule-based path is a real point of difference worth stating explicitly in-product ("no plan limit, ever" as a small trust signal near the paste box), not just implied by the absence of a paywall.
- < cite index="33-1">EverSQL's paid tiers are metered by a monthly optimization count (10/month on the cheapest paid plan) rather than by seats or time</cite> — reinforcing that the entire competitive set treats plan/query analysis as a metered resource. This is useful ammunition for positioning copy (see Landing Page Positioning brief) but also a reminder to actually build the rule-based path as unlimited by architecture (fully client-side, per the Technical Spec), not just unlimited by current policy that could quietly change later.

## 5. Trust/storage defaults matter more than technical capability

- < cite index="6-1">A user explicitly avoided using PEV2's hosted version for their organization even after confirming it could run purely locally, because the hosted default stores plans server-side and that was enough to trigger institutional distrust</cite> — this is strong evidence that *default behavior and the clarity of that default*, not raw technical capability, is what determines whether a cautious team will actually use a tool on real production plans.
  - **Implication** (reinforces Technical Spec §6, now with concrete evidence): PlanReader's "nothing leaves the browser" claim needs to be verifiably true by default and stated in plain language exactly where the paste box is, not just documented — the PEV2 case shows that even a technically-correct local-mode option gets ignored by skeptical users if the *default* experience they'd naturally land on stores data server-side.
- Conversely, < cite index="91-1">PEV2 ships a fully offline, no-install `pev2.html` file that can be downloaded and opened directly in a browser with zero server dependency</cite>, which is a genuinely trust-maximizing option for the most locked-down environments. This is worth considering as a low-effort Phase 2 addition for PlanReader — a single static HTML file that runs the rule-based engine with zero network dependency at all, for teams whose policies won't allow even a normal "your browser fetches static assets from our CDN" web app.

## 6. Node-to-query correlation is requested but consistently under-built

- < cite index="6-1">Pev's original author noted that highlighting the relevant part of the original query text when a plan node is selected is "quite rudimentary at this point"</cite> even in a tool built specifically around that idea — no tool in the competitive set does this well, including the ones focused on beginner-friendliness.
  - **Implication**: this is a legitimate Should-have candidate for PlanReader (link each plan node back to the specific clause of the submitted query, when the query text is available) — it's consistently wanted, consistently under-delivered elsewhere, and directly reinforces the "plain-language, beginner-first" positioning, since it answers the very natural question "wait, which part of *my query* is this node?"

## 7. Net changes this suggests to the existing deliverables

- **Feature Prioritization**: add a Must-have parsing-robustness item — tolerant JSON parsing (duplicate keys), common copy-paste artifact stripping (`\x`-mode, log prefixes), and non-root `ShowPlanXML` handling — since these aren't edge cases, they're routine real-world input.
- **Feature Prioritization**: add a Must-have rule — explicit labeling of cumulated/parallel/looped timing figures, so PlanReader doesn't reproduce PEV2's still-open confusion.
- **PRD**: add a stated, honest limitation in the "non-goals" framing — PlanReader explains the plan it's given, and will say so plainly when a query's behavior looks parameter- or input-sensitive rather than implying the single pasted plan is the full story.
- **Technical Spec**: note the "no plan-count limit, ever" architecture as a deliberate, stated contrast to every free-tier competitor reviewed.
- **Landing Page Positioning**: the "no signup, nothing stored" claim should be positioned as a *default*, stated directly next to the paste box, not just a documentation/footer fact — directly informed by the PEV2 trust case.
